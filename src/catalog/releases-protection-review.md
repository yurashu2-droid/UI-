# Releases: protecting the original

This is a presentation-only upgrade of the existing `site_github_releases` teaching page. It does not add a 29th template. Its initial ZIP, commit, cache and PDF retain the exact existing part types, labels, rectangles and native controls. The separate module is not registered in the catalogue yet.

The useful distinction is **protection of a particular original**, rather than a new file-library skin or another replay-routing lesson. A cache can block a cover without increasing measured damage. It cannot produce the first payload, protect every asset, redirect the opposing popup or become a real GitHub cache/download feature.

## Motif and original content

GitHub's official [About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) documents release notes, tags and downloadable assets. Its [source code archives guide](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives) documents the release Assets section and downloadable ZIP/tar snapshots. These references were checked on 2026-10-03 and establish only the page motif, not a correspondence between real GitHub behavior and combat mechanics.

A file-library proposal was not retained. The official [Google Drive organization guide](https://support.google.com/drive/answer/2375091?hl=en) describes folders, moving files, stars and details. Recreating those structures with the current parts would largely repeat the existing Releases assets, Trello attachment routing, Figma nesting or Slack attachment thread. No sharing, folder operation or library service is implemented here.

The new instructional copy and CSS are original. There are no copied provider assets, external media, network actions, service downloads, account operations or new combat definitions. The cache remains the native game cache. Existing native controls retain their local previews and battle feedback.

The fixed explanatory blocks leave all three cache rectangles clear. The PDF-side and detached alternatives occupy overlapping regions with each other, but only one cache is present at a time. These are editing coordinates, not new clickable download controls or a new targeting API.

The popup's real target remains the ZIP, whose opening packet is 30 versus PDF's 18. Protecting the PDF does not make the popup attack that PDF. The cache starts with one charge and, after a block, refills one charge on its actual period (base eight seconds). It does not stack charges. At CPU10 or greater without other bonuses, the ZIP first fires at 4 seconds; commit's first 3.5-second check has no original, so its first actual replay is 10.5 seconds.

## Reproducible combat conditions

Unless explicitly stated otherwise:

- Ordinary canonical combat-v4, 0.05-second fixed ticks
- 24 seconds (480 ticks), both sides HP10,000 and CPU12
- No administrators, no audience/server-pressure experiment
- Normal production startup clocks; no preloaded payloads, charge or income
- Both player/enemy seats checked with the same logical boards
- HP damage is recorded separately from shield absorption, natural attack count, replay count and prevented covers

The following 24-second meters are unfinished diagnostics, not victories. Their opponents are purpose-built fixtures and are **not equal-price/equal-load matchups**.

## Costs and counterplay

At **CPU8**, below the normal starting capacity of 12, the plain-pressure fixture produces a genuine cost reversal. With cache deployed, the page has CPU10, 1.15 lag, 162 HP damage and 21.6HP lost to overload at 24 seconds. Stashing only cache leaves CPU8, no lag, 192 HP damage and no overload loss. Both seats reproduce this comparison. This is an under-capacity diagnostic, not a normal-start recommendation to discard cache.

Storage preserves ownership, the original label, dimensions and cash. The active board drops from $24 to $19 acquisition-equivalent and loses the cache's 12,672px² occupied rectangle; the player still owns all four parts and their full $24 ingredient value. Deployment and storage use the existing move/save contract, not a refund or new resource rule.

The witness uses ordinary IDs but does not demonstrate actual paid acquisition. The Releases template has no healing, shielding or income, and its cache does nothing against these normal attacks.

The supported browser route previously returned `ERR_BLOCKED_BY_CLIENT`. It was not retried, bypassed, replaced with headless Chromium or moved to the user's computer. Browser pixels, wrapping, zoom, responsive readability, actual clicks, hover, keyboard order and screen-reader acceptance remain unverified. Source geometry and contrast calculations cannot certify those behaviors.

## In-place registration

The catalogue uses `RELEASE_PROTECTION_TEMPLATES` as a **replacement** at the existing Releases position (zero-based template index 15, laboratory opponent index 29), not as an appended template or opponent. The decoration resolver calls `releasesProtectionDecor`, and the catalogue stylesheet imports `releases-protection.css` beside the existing Releases stylesheet. The original Releases file remains the baseline source so there is no import cycle or duplicate identity. The default gameplay layout is identical.

Historical append-prefix tests retain their original digests by normalizing only this exact entry’s reviewed tip, counterplay and decoration fields (and its preset description) to the unchanged baseline. Identity, combat, default geometry, native labels, references, ordering and all other entries remain covered. Separate registration and real-renderer tests verify that only those three teaching fields differ, all 42 laboratory indices and 28 template entries remain, and the new inert lesson renders alongside the four original controls. These source/DOM-adapter checks are not browser acceptance.
