## Recent candidate decisions

Each decision below distinguishes a rejected proposal from a registered experiment. None of the added UI definitions has been promoted to the default acquisition pool. Additions should fill a useful choice, not merely rename an existing damage or shield number.

1. **Unread RSS queue UI — deferred after source review**: the initial cost 6 / load 2 / 4.8-second / 35% proposal does not yet prove a niche. Two generic credits can be filled by one fast attacker; throughput is below search pagination at the same cost/load. A credible prototype would require two distinct canonical text-attack types, coalesce repeated events into one pending stamp per source, dispatch only one source per pulse, skip covered entries without replaying them, and expire unread permission in fixed ticks. Use the source's latest natural payload rather than banking an old Lucky critical. A dispatch absorbed by defenses must still consume its stamp. This needs a controlled comparison with existing references, pagination and financed popup before adding any catalogue entry. A second source review found the fallback benefit is mainly avoiding a covered primary: over an unmodified24-second steady window its five35% dispatches surrender12.5% of pagination's four50% dispatches before expiry. Cheaper7-second commits or6.5-second references can already avoid the particular6-second popup/pagination phase lock. Keep this deferred until a financed-popup, full-phase, equal-resource comparison proves value over those choices; freeze priority and expiry-refresh semantics first. If the timing benefit is not worth the extra rules, use RSS as a visual template instead.

## Rules for future batches

- Append newly registered templates to the end of `SITE_TEMPLATES`; do not reorder or remove existing entries without a save migration. Laboratory opponents currently persist a numeric stage, so changing old positions can silently select a different opponent.
- Keep part IDs and gameplay tags canonical. Appearance and provenance remain optional safe references and do not affect combat hashing.
- A new targeting field must be frozen with the definition and included in the canonical gameplay fingerprint. `replayTags` is the existing example.
- New controls must have a meaningful local preview or explicitly be inert decoration. A form must not inherit the search-submit handler accidentally.
- Preserve source-native silhouettes and controls across themes and imported appearances. Gameplay feedback must use the existing live DOM, not fabricate an unrelated card.
- Protect container geometry: fixed header content must fit the declared padding, including long edited labels.
- Define event/resource, phase, scope, counter and opportunity cost before adding a new engine rule. Natural payload, control recovery, shared conversion and shared-rate-budget contracts apply to every new family.
- Validate legal progression and resource tradeoffs before promotion. Do not compensate for a weak template by silently giving it exclusive counters or unlimited admin slots.

### Restore comparison brief

The approved comparison passed its isolated prototype review and the real experimental entry passed independent integration verification. The protected completed checkpoint remains the reference. Selected contract:50% of eligible ordinary loss, cap12, base5-second period,100-tick exclusive expiry, zero-loss/pure-pierce overwrite, successful-only activation. The core engine owner owns the real-definition and paid-trial comparisons.

- Incoming record: the latest real HP loss caused by an opponent's UI packet, after existing shield, limiter and audience calculations. Cart attacks are still opponent UI attacks, so include them in the comparison rather than inventing a special immunity. Overkill, own-ad churn, overload and admin damage do not enlarge the record.
- Shared ownership: one record per defending page; duplicate restore controls cannot each redeem the same loss. Consumption cannot revive a page, undo a finished battle, or reuse pre-backup history.
- Candidate comparisons: fractions25/35/50%, caps8/12, native periods3/5 seconds, short fixed-tick expiry. These are search inputs, not settled catalogue stats. Compare including/excluding direct piercing and clearing/retaining the record on fully blocked attacks before choosing a contract.
- Baselines: real legal replacements against wish-list healing, document-linked notices, shields and429; preserve budget, CPU, space and acquisition costs. Test ordinary heavy packets, PDF, small frequent packets, big-hit-plus-chip, and synchronized heavy packets. Do not infer a counter from one favorable initial phase.
- Native UI: a small version-history panel, one visible pending revision, timestamp, source UI name, bounded recoverable HP and expiry, plus a local Restore button. A consumed record becomes visibly read; overwrite changes the single row. Avoid showing several stored revisions when gameplay only owns one. Restoring should not animate new visitors arriving or claim real files were changed.
- Public visual meaning: [Google Docs version history](https://support.google.com/docs/answer/190843?hl=en) and [Notion restore preview](https://www.notion.com/help/duplicate-delete-and-restore-content) establish the familiar history, preview and restore vocabulary. The game would use original markup and fictional history, with no document-service connection.
- Promotion gate: reject the part if phase-controlled equal-resource comparisons cannot show a useful large-packet niche without broadly displacing ordinary heal or neutralizing the existing PDF/fortress tradeoff. Any retained prototype stays experimental and needs independent source/contract review; pixel verification is still outstanding.
