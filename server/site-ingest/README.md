# Static public acquisition boundary

By default, this development service fetches only these complete, fixed HTTPS URLs:

- `https://books.toscrape.com/` (a public no-JavaScript scraping practice site; https://toscrape.com/)
- `https://example.com/`

It is not an arbitrary URL proxy. User-supplied paths, queries, credentials, ports and redirects are not accepted. It fetches one HTML document (512 KiB decoded limit) and, for code reconstruction only, at most one specifically allowlisted stylesheet (256 KiB decoded limit). HTML and CSS each have a 15-second deadline, the combined acquisition has a 30-second deadline, and the browser client gives the operation 35 seconds. It parses inertly with parse5, excludes scripts/hidden content/form values, and exposes only bounded metadata or a validated safe blueprint. Raw HTML, arbitrary CSS, URLs and source scripts never reach the game DOM. Only one fetch per service instance runs concurrently.

## Current status

`GET /api/raid-captures/capabilities` explicitly reports `publicStaticCapture: false`, `publicCodeReconstruction: true`, `publicStaticProbe: true`, `sourceJavascript: false`, and `networkIsolation: false`. Code reconstruction does not need a browser renderer and does not claim browser isolation or measured source pixels.

`POST /api/raid-captures/probe` with `{"url":"https://books.toscrape.com/"}` can verify real source acquisition. A successful fetch returns HTTP 503 with `code: "renderer-unavailable"` and verified byte count/content hash. This is deliberately **not** a playable blueprint or a completed visual capture.

`POST /api/raid-captures/code` with the same URL body performs that fixed-source fetch, then creates a playable **code approximation**. It uses actual heading/link/product/purchase text, tag names, bounded class hints, source order and product grouping. Long category lists cannot consume the product quota. Supported CSS consists of safe colors, generic font families, bounded pixel font sizes/padding, normal/bold weight, text alignment, solid borders, corner radii and hidden flags. Simple tag/class/id selectors connected by bounded descendant or direct-child (`>`) relationships are interpreted as data; stylesheet text is never injected into the page. Hiding is conservative: a supported rule that hides an element is not undone by a later unsupported display reset. This is not a complete cascade: media/support queries, pseudo-selectors, custom properties, relative units, external fonts, images, scripts and CSS resource functions are ignored. Font sizes and padding can be reduced to keep the canonical control readable.

The only linked asset allowed is `https://books.toscrape.com/static/oscar/css/styles.css`, and only when the fetched Books HTML declares that exact stylesheet. Alternate, disabled and non-screen stylesheets are skipped. Imports and URLs inside CSS never trigger requests. Redirects, response URL mismatches, non-CSS MIME, oversized bodies and asset timeouts cause an explicit HTML-only fallback. Source HTML and acquired stylesheet hashes are kept separately in the snapshot. Parsing is capped at 256 KiB of combined stylesheet text, 4,096 top-level blocks, 1,024 accepted selector rules, four simple selector parts and 64 declarations per rule. Budget truncation is recorded in `analysis.css.limited`.

Eligible embedded styles and the acquired stylesheet now follow their declaration order in the parsed HTML for the supported selector/declaration subset. The server matches the acquired sheet's verified URL to its actual eligible link; unrelated or inactive links cannot change that position. Repeated eligible links to the same acquired bytes use the last position, with one fetch and one CSS-budget charge. This fixes equal-specificity color overrides placed before a linked sheet; the declaration-order behavior is covered by regression fixtures. Specificity and inline-style handling remain bounded approximations; `!important` precedence and a full browser cascade are not implemented. No stylesheet URL is added to the saved blueprint, and old manifests remain readable.

Within a declaration block or inline style, comments are inert token boundaries. Semicolons inside quotes, escaped text or nested ignored values cannot create new declarations or hide source elements. Escapes remain unsupported values, not decoded CSS. Malformed or unfinished strings, comments, escapes and nested values conservatively discard the unfinished declaration and remaining text, while preserving prior complete declarations. The existing 4,096-character block/inline limit and conservative 64 raw-semicolon-segment ceiling are checked before lexing; even semicolons inside ignored data still consume that ceiling. No property, selector, resource or acquisition limit is expanded. A source-derived Books regression varies only inert comments/quoted values and keeps its eight original components; the untouched recorded Books capture and all historical fixture hashes remain identical. This is syntax compatibility for the existing approximation, not a full CSS parser or browser verification.

At the enclosing rule-block boundary, braces inside comments and quoted strings (including escaped quote/brace text) no longer cause an otherwise supported rule to be discarded. The existing quote/comment-aware scan distinguishes them from actual nested blocks; nested rules, at-rules, unfinished blocks and unquoted brace escapes remain unsupported. A source-derived Books case previously lost the navigation padding after adding only inert brace text, changing its text rectangle from `(15,10,162,20)` to `(12,8,168,24)`. It now preserves the original eight appearances and 576 accepted rules. The untouched recorded CSS has no such inert opening braces, so its sealed capture and appearance IDs stay unchanged; changed source bytes still receive distinct provenance. All existing byte, block, selector, declaration, resource and acquisition limits remain unchanged.

Direct-child matching requires the immediate parent, while mixed descendant/child chains can try an earlier ancestor when a nearer candidate fails its parent constraint. The same four-simple-part, rule, declaration and source-size limits remain; sibling combinators, attributes, pseudo-selectors and malformed relations are still rejected. The analyzer still rejects source depth above 64 and more than 20,000 nodes before style analysis.

For the recorded Books HTML/CSS, this changes only the top “Books” navigation label's source-derived text rectangle from `(12,8,168,24)` to `(15,10,162,20)`, reflecting `.nav > li > a { padding: 10px 15px; }`. The seven remaining components (including Travel/Mystery), combat rectangles, prices and source hashes remain unchanged. Accepted safe-rule metadata rises from 424 to 576 without hitting the existing limit. Newly acquired manifests receive a new content-sealed capture ID and Books appearance ID; the other seven appearance IDs are unchanged. Existing saved blueprints, trophies and pending rewards keep their original appearance bytes and IDs. The compatibility fixture and real storage/registry tests cover both records coexisting. This remains synthesized game geometry, not measured source pixels.

The resulting `code-v1` / `code-approximation` blueprint includes a SHA-256 of the HTML actually analyzed, low-confidence inferred-layout metadata, and `sourceRect: null` on every component. `combatRect` is a synthesized legal game layout. The UI must keep “コード解析による近似配置” visible through selection, battle, loot and collection. A win grants the frozen **approximate enemy element**, not a claim of original website pixels. Empty JavaScript shells produce an explicit no-playable-elements error. Hash verification, canonical balance/geometry validation and source-origin matching are required before play. Existing authored fixtures remain distinct.

The development plugin `raidCapturePlugin()` registers this middleware; a static production build does not provide a capture server. No public host, account, credential or deployment is configured.

## Local HTML/CSS import: separate laboratory-only boundary

The local importer is a client-side path in `src/raid/local-import-client.ts`, `local-import-controls.ts`, `local-import-worker.ts`, `local-code.ts` and the shared code reconstruction modules. It neither calls this HTTP service nor expands its public-source allowlist/capabilities. Open the laboratory's own-page editing view, choose the menu's “URLレイド”, select “HTMLファイル” plus an optional “CSSファイル（任意）”, then explicitly press “ローカルHTMLを近似再構成”. Selecting files alone does not analyze, select an opponent or grant a reward.

After an accepted local reconstruction, one verified blueprint can be retained in transient same-tab return memory for the same live laboratory run/profile. A player may lose, close to edit, then explicitly resume that approximation without reading the original files or making another parse/network request. Pending wins take priority. The slot contains no File objects or raw HTML/CSS and is not part of any save/archive; reloading or changing its owner loses access. Clearing the slot does not alter the currently displayed opponent or acquired collection. Selection painting precedes optional retention verification, and cancellation/owner changes cannot create a hidden challenged opponent or late retained result.

- HTML must be one nonempty `.html`/`.htm` file of at most 512 KiB. Optional CSS is one file of at most 256 KiB. Both decode strictly as UTF-8; malformed UTF-8 is rejected, not repaired. Eligible embedded stylesheet text plus the selected sheet must total at most 256 KiB, even with no CSS file selected. Over-budget local stylesheet input is rejected rather than silently reduced to HTML-only.
- The CSS basename must match `[a-zA-Z0-9][a-zA-Z0-9._-]{0,119}\.css`: ASCII only, with a lowercase `.css` suffix. Exactly one eligible HTML stylesheet link must have `href` equal to that basename or `./` plus it, without URL/path resolution or case folding. It must be active, non-alternate, non-disabled and screen-eligible under the existing type/media rules. The selected bytes participate at that link's source position relative to eligible embedded styles. No match or more than one match is an error. Subdirectories, parent paths, absolute URLs, query/fragment variants and percent-encoded URL variants do not match. The picker does not inspect directories or prove the two files share an actual filesystem directory.
- “CSSなしに戻す” explicitly clears the selected CSS; only supported embedded/inline styling then applies. A CSS mismatch never silently ignores that selection or fetches a replacement. Folder selection, relative-directory uploads and ZIP traversal are unsupported.
- One disposable module Worker parses inertly with parse5, with construction-time node/depth guards (20,000 nodes/depth 64), the existing bounded CSS selector/declaration subset and legal canonical geometry. The 5,000ms client deadline begins before file reads and remains active through result validation. Cancellation, newer selection, disposal and live lab-ownership checks terminate active work or ignore late results. Native `File.arrayBuffer()` reads themselves are not abortable here; a read may finish after cancellation but cannot create a Worker or update selection. Worker startup failure is explicit; no synchronous parser fallback is used.
- Supported candidates are bounded static headings, links, recognized purchase/product controls, search forms and labeled checkbox structures. JavaScript-only shells, arbitrary styled divs/canvas apps and generic controls outside that semantic subset are unsupported. No playable elements produces an error, not a fabricated opponent. The resulting `code-v1` / `code-approximation` still uses synthesized 960×680 game geometry, low confidence and `sourceRect: null`; it does not preserve the whole page, run source behavior or supply an original-page comparison.
- Source JavaScript is never run. No raw source HTML/CSS is inserted into the game DOM, and local content is never loaded in an iframe. No source images, media, fonts, CSS imports/URLs or extra assets are requested. Source files are neither uploaded nor sent to a third party. Only bounded text/appearance primitives enter the canonical renderer; module loading for the game's own Worker is separate from source-resource acquisition.

### Explicit local checkbox labels

The local-only branch in [`src/raid/code.ts`](../../src/raid/code.ts) also recognizes a separate HTML `<label for="news">Receive updates</label>` associated with an HTML `<input id="news" type="checkbox">` in the same parsed document tree, before or after the label. It maps one eligible caption per checkbox to the existing `gov_check` approximation. The label supplies bounded visible text, safe style and structural provenance; input values and ARIA names do not supply the caption. This does not add a combat definition or change the public URL analyzer. The HTML checkbox’s source-default `checked` attribute is not copied into the appearance or the game-owned live checkbox. Presence forms such as `checked`, `checked=""` and `checked="false"` therefore do not create a checked appearance cue; this is an unsupported source-state detail, not an interpretation of the last spelling as false. Input values, ARIA, CSS state selectors and live/script properties are not used to infer it. The game checkbox remains a separate control; importing a skin does not set its checked state.

- `for` is an exact, case-sensitive ID match, with no trimming, selector evaluation, fragment resolution, token-list interpretation or `name` fallback. An empty value or one containing ASCII whitespace/control characters is rejected. Missing, wrong-type and conflicting targets do not fall back to a different nested checkbox.
- Duplicate IDs anywhere in the same indexed document tree make an explicit association ambiguous, even when a duplicate is hidden, inert, omitted or foreign-namespace content. Template contents belong to a separate omitted tree and are neither targets nor duplicate IDs for the main tree. The label and target must themselves be HTML-namespace elements in eligible ancestry; hidden/ARIA-hidden/supported-CSS-hidden, inert, omitted and foreign subtrees cannot contribute a label or target. `datalist` contents are also excluded.
- Nested labels, multiple labelable descendants and a contained control conflicting with `for` are rejected. An eligible existing wrapped label takes precedence over an extra external label; otherwise the first eligible label in parsed tree order wins. This avoids duplicate combat parts and preserves valid wrapped-label analysis and sealed regression output.
- Eligibility is evaluated on the tree parse5 actually constructs, including its HTML error recovery, not on apparent tag nesting in source text. A malformed source that parse5 repairs into ordinary eligible HTML is judged by that repaired tree. This is not a raw-markup validator or a full browser accessibility-name/label algorithm. In particular, conservative duplicate/conflict rejection is stricter than the browser's first-matching-ID rule described by the [HTML label specification](https://html.spec.whatwg.org/multipage/forms.html#the-label-element).
- The existing 512 KiB HTML, 20,000-node/depth-64 parsing, CSS, candidate and game-geometry budgets still apply. IDs and labels are indexed over the already bounded tree; ancestry checks use its bounded depth. The existing per-kind/per-region quota remains 12 and the candidate ceiling remains 64. No resource request, raw-source persistence, schema change or public-source reinterpretation is added.

[`raid-local-checkbox-labels.test.mjs`](../../tests/raid-local-checkbox-labels.test.mjs) covers exact associations, exclusions, conflicts, same-tree behavior, one-candidate precedence, canonical reconstruction, hidden/private-value omission, valid wrapped-label hashes and source/candidate bounds. Historical public/fixture capture identity remains on the unchanged public path. These are parser/blueprint contracts, not evidence of browser label activation, native file picking, Tab order, assistive technology or source-pixel fidelity.

On failure, cancellation or a stale result, the previously selected opponent and saved rewards remain intact. After successful analysis, “このページに挑戦” uses the existing laboratory battle → real victory → explicit single-UI claim flow. Selection alone grants nothing. Import, local challenge and local claim require a live laboratory edit context; story cache/energy/receipts and campaign challenge/claim reject local captures at domain boundaries as well. Outside the laboratory, local pending victories are retained but filtered from resume selection, with lab-recovery guidance; eligible public pending rewards retain priority over a new capture request.

Local provenance uses `source.kind: "local-file"` and `source.displayUrl: "local://" + analysis.sourceHash`, with exact original HTML-byte SHA-256 and separate selected-CSS-byte hashes. A decoded UTF-8 BOM is retained for provenance. Filesystem paths, selected filenames and raw HTML/CSS are not persisted; bounded source-derived titles, text, class hints and structural node paths can be part of the safe approximation. Structural node paths are not filesystem paths.

This adds a source kind within blueprint schema 1. Older builds reject new local-file captures rather than treating them as public URLs or silently migrating them. Existing public/fixture hashes, saved capture/appearance bytes and old collection archives are not resealed or reinterpreted. The collection archive envelope and its 256-entry/256-capture/16 MiB limits remain unchanged. Local cosmetic skins use the existing lab-add/owned-canonical-reskin rules, without adding campaign or online acquisition. Content hashes and unsigned archives prove consistency only, not that a victory actually occurred. See [the user walkthrough](../../README.md).

Native browser file picking, cancel/reselect, actual click/keyboard/assistive-technology behavior and visual acceptance remain unverified because the supported browser route is blocked. Worker/DOM adapters or emitted-module checks are not browser acceptance.

### Explicit local input purchase labels

The normalized, bounded nonempty caption must match the existing purchase words, such as `Buy`, `Add to cart`, `購入` or `カート`; it maps to the existing `am_buy`, with inferred game geometry. Only this explicit visible action-label attribute is used. A fresh local capture containing a newly recognized input before an ordinary button can therefore select that input first. ## Local opaque RGB colors

Only the local-file analysis path opts into a finite literal sRGB subset before existing safe-style validation. This improves the colors of supported text, flat backgrounds and solid borders; it does not measure browser layout or broaden URL acquisition. Embedded styles, the one explicitly selected/matched stylesheet and inline declarations use the same reader. Existing selector/cascade/inheritance rules and all declaration/byte/block/rule/parse/Worker deadlines remain unchanged.

Supported forms follow the relevant [CSS Color 4 RGB grammar](https://www.w3.org/TR/css-color-4/#rgb-functions):

- `rgb()` and `rgba()` are case-insensitive aliases, with exactly three signed decimal channel literals; each may use `%`. Exponent notation is deliberately unsupported.
- Comma syntax requires all three channels to use numbers or all percentages; optional alpha is separated by a comma. Space syntax permits mixed channel units; optional alpha follows `/`.
- Numeric channels clamp to 0–255, percentages to 0–100%, and normalize to nearest 8-bit `#rrggbb` values. Alpha must be absent or fully opaque after clamping: a numeric value at least 1 or percentage at least 100%.
- Only existing `color`, color-only `background`/`background-color`, one `border-color`, and the existing three-token solid-border shorthand accept the normalized value. No new properties or background-layer grammar are added.

For example `rgb(18,52,86)` and `rgba(18 52 86 / 1)` become `#123456`. Nonopaque alpha, missing/extra channels, mixed comma-channel units, mixed separators, `none`, relative colors, nested functions, `var()`/`calc()`, other color spaces and resource syntax remain outside this supported subset. Unknown functions do not reach rendering, source code is never executed, and this extension makes no network request.

The public/default reader remains on its previous behavior, including public captures containing RGB declarations. Existing non-RGB local captures remain identical. Newly analyzed local source with newly supported RGB can produce different style primitives, analysis counts, blueprint hashes and capture IDs; this intentional change does not rewrite an existing snapshot. Old stored RGB approximations retain their bytes and hashes even after a new RGB-aware acquisition. Local provenance, archive schemas, canonical control geometry, progression isolation and reward rules are unchanged.

`tests/raid-local-rgb-colors.test.mjs` covers declaration grammar and rejection, embedded/selected/inline styles, inherited text/fills/borders, bounded rule processing, unchanged public/non-RGB whole-result hashes, Worker result verification, matching equivalent hex appearance, and old/new collection round trips. These are source/Worker/serialization checks, not browser pixels, full CSS support or a visual-fidelity percentage.

## Local explicit input-type selectors

Only new local-file analysis enables a narrow exact-type selector extension. An explicitly named HTML `input` compound may contain exactly one unnamespaced `[type=submit]` or `[type=button]` equality test, with the existing optional id/classes before or after it and existing descendant/child structure (at most four selector parts). It accepts bare, single-quoted or double-quoted literal values; CSS ASCII whitespace inside the attribute notation; and ASCII case variants of `input`, `type`, `submit` and `button`. Id/class case remains on the existing path. Attribute equality contributes the existing class-like score of ten within the bounded scoring model, not a claim of complete browser cascade semantics.

Matching requires the HTML namespace and the actual unnamespaced `type` attribute, ASCII-case-folded. Missing values, spaces inside the quoted/raw value, invalid values and HTML's default input type are not repaired into a match. No other attributes/types, existence/operator tests, namespace syntax, flags, pseudo/state selectors, escapes or comment-bearing attribute lists are added. See the primary [attribute-selector grammar](https://www.w3.org/TR/selectors-4/#attribute-selectors) and [HTML selector case rules](https://html.spec.whatwg.org/multipage/semantics-other.html#case-sensitivity-of-selectors).

The local reader chooses the new path only for an actual `[` outside strings/comments/escapes. Its list scanner keeps quoted, bracketed and parenthesized data together and splits only top-level commas; unsupported functions are not interpreted, and their interior fragments cannot become supported rules. New typed-selector grammar is disabled on the old list path, so a quoted fragment cannot gain new support. The original raw-comma cap of 128 remains, including commas inside quoted values/functions; all existing byte, block, rule, declaration, selector-part, HTML-construction and Worker limits remain.

This can apply source color, solid border, padding or radius to a purchase control already recognized by the local importer. It adds no canonical control, private-value/label reading, source-code execution, fetch target or campaign/online reward route. Existing hidden/inert/private/foreign-element eligibility is still checked. A newly matched `display:none` rule can remove a candidate rather than guarantee an unchanged number of controls.

Public/default parsing and its complete recorded outputs stay unchanged. Genuine no-attribute local inputs retain their previous whole-result bytes. Fresh local attribute-bearing lists can intentionally change appearance, analysis counts and seals both through newly supported type matching and by removing formerly manufactured comma fragments from quoted or unsupported function content. Existing stored captures, pending rewards, claimed appearances and archive exports/imports retain their original bytes; they are not reinterpreted by the new parser.

`tests/raid-local-input-type-styles.test.mjs` exercises exact grammar, raw values and namespaces, source order/specificity, malformed/quoted/function list rejection, existing limits, unchanged public/no-attribute hashes, real Worker results and old/new archive round trips. Independent review also executed the built Worker with source-script/network/DOM tripwires. These are bounded static parsing and serialization proofs, not browser pixels or broad CSS support.

## Verified runtime blocker

In this runtime, a user/network namespace can be created and public HTTPS fetches succeed. Chromium launched on `about:blank` inside the network namespace, without disabling its sandbox, aborts with process-singleton `socket() failed: Operation not permitted` (exit 134). No page data was rendered in that probe. `bwrap` also fails while attempting a NETLINK_ROUTE socket. Direct `dns.lookup` fails with EAI_AGAIN, whereas the runtime-brokered fetch works, so application-level DNS pinning has **not** been demonstrated.

Do not use `--no-sandbox`, single-process mode, browser-extension disabling, a localhost-navigation workaround or user-computer switching to hide these restrictions.

## Local native search controls

New local-file analysis additionally recognizes an HTML-namespace native `input` with an explicit exact ASCII-case-insensitive `type="search"`, or an eligible HTML `search` region containing one or more such inputs. The attribute is not trimmed or defaulted. A selected region represents its eligible inputs once using the region's own style/path/order; otherwise an independent eligible input uses its own. Other supported child headings, links and checkbox candidates remain independently eligible within existing selection limits.

These new candidates always use the generic caption 「検索」. They do not read input values, default values, placeholder, title or ARIA names as source labels. `form=` presence, including an empty value, excludes a new input candidate rather than resolving an external owner. Ordinary text/password/implicit inputs, empty or results-only search regions, arbitrary div/ARIA widgets, foreign namespaces, hidden/safe-CSS-hidden/inert or omitted ancestry, datalist, and control/link ancestry are outside the new subset. Visible eligible nested search regions invalidate the enclosing/nested new regions; hidden/inert/omitted nested markup does not suppress an otherwise eligible visible sibling.

Existing reachable search-form candidates take precedence inside or around a region, avoiding duplicate search parts. Their legacy form eligibility and names are deliberately unchanged, including historical inert behavior. Hidden/omitted forms are unreachable and cannot shadow the new local path. A form containing only a mixed-case `type="SEARCH"` that the old branch did not recognize can yield a new input candidate; it is not silently renamed or reclassified as a legacy form. These conservative policies use parse5's repaired tree and bounded parent walks, not browser accessible-name computation or live form behavior.

The meaning of [native input search](https://html.spec.whatwg.org/multipage/input.html#text-(type=text)-state-and-search-state-(type=search)), [the HTML search element](https://html.spec.whatwg.org/multipage/grouping-content.html#the-search-element), and [ASCII-insensitive enumerated keywords](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#keywords-and-enumerated-attributes) informs the subset; support for all valid HTML or browser layout is not claimed. Disabled/readonly controls may still be represented as static appearance, without becoming executable controls from the source.

Public/default analysis and unchanged eligible legacy forms retain complete output compatibility. Newly eligible local markup can change candidate counts, selected parts, appearance and fresh capture IDs, while raw source hashes keep their existing meaning. Stored pending/claimed/archive captures are never reparsed or rewritten. Existing byte/node/depth/candidate/CSS limits, Worker cancellation, inert parsing, local provenance and laboratory-only acquisition boundaries are unchanged. No input execution, new CSS selector grammar, external fetch, directory access or automatic upload is added. The [one-file example](../../examples/local-raid/README.md#フォーム外の検索欄を比べる見本) demonstrates the supported scope; actual browser rendering and file-picker acceptance remain unverified.

## Local PDF filename hints

Local-file analysis can classify an eligible ordinary HTML anchor as the existing `pdf` evidence / `gov_pdf` part when its advertised source path has a nonempty basename ending in literal ASCII-case-insensitive `.pdf`. This is a filename hint, never a MIME/content/existence claim. The importer performs no destination fetch, file read, open, download or source execution. No new canonical part, network allowlist, schema, archive migration or campaign/online reward path is added.

The new branch requires the existing nonempty visible-caption approximation and an unowned anchor outside existing product ownership, forms, native control containers, omitted/foreign/hidden/supported-CSS-hidden/inert ancestry, canvas fallback and closed dialogs. All closed `details` are conservatively excluded, including their normally visible first summary; this is not a complete visibility model. Excluded anchors retain their precise legacy behavior, which may still produce ordinary navigation. This does not broadly repair legacy visibility or form semantics.

The HTML-parsed href is limited to2,048 code units. Only surrounding ASCII whitespace is trimmed. Internal whitespace, controls, backslashes, replacement characters, malformed or unsupported schemes/authorities and credentials are rejected. Ordinary path-relative or root-relative paths qualify only when no document `base[href]` makes their base unresolved; explicit `http://` and `https://` paths are also eligible. Scheme-relative URLs, `file:`, `data:`, `blob:`, script/mail and other schemes, query/fragment-only values, PDF directory names and encoded source-path escapes are excluded. Query/fragment suffixes may follow a qualifying path but cannot establish its type. Raw Japanese/Unicode basenames such as `資料.pdf` are eligible; the URL serializer's later UTF-8 encoding is distinct from percent escapes already present in source. The helper never percent-decodes. `download`, `type`, title and ARIA do not establish eligibility or a caption.

The existing traversal, quotas, candidate selection and geometry remain in control. A fixed warning is saved only if a newly eligible PDF hint is actually selected: 「PDFはリンク先のファイル名による表示上の手掛かりです。リンク先のファイル・MIME型・内容は取得・検証していません。」 The helper does not return or persist href, query, fragment or filename. Existing visible caption text remains subject to the ordinary caption rules; raw HTML continues to contribute only through the existing source hash.

Fresh newly eligible local analyses can change evidence, canonical selection and capture seals. Public/default results and excluded/unaffected local results preserve their bytes; stored old captures are validated and restored without re-parsing. Real laboratory victories and one-time claims can retain an old navigation capture and a fresh PDF capture together in the unchanged appearance archive. The emitted bounded/cancellable Worker remains the execution boundary. The [standalone sample](../../examples/local-raid/README.md#pdfというファイル名の手掛かりを比べる見本) contrasts two filename hints and two ordinary links without supplying or opening any PDF.

The [HTML anchor definition](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element) and [URL writing rules](https://url.spec.whatwg.org/#url-writing) inform these conservative checks; successful URL parsing alone is insufficient because browsers can repair input. These are source and Worker guarantees, not verified browser pixels, native picker behavior, complete CSS fidelity or accessibility acceptance.
